# Design: sentence-list-playback

## Context

這是一份可以直接用瀏覽器開啟的單一 HTML 檔: 沒有 build step, 沒有 package manager, 沒有後端, 樣式與行為都內嵌在同一份檔案裡. 現有狀態只有兩個: 語速與音色, 兩者都存在瀏覽器本機儲存. 播放能力來自瀏覽器內建的語音合成 API.

這三件事構成本次設計的主要限制:

- 使用方式是「直接開檔」, 不能假設有 local server. 這排除了把程式碼拆成 ES module 檔案的做法 (瀏覽器對 `file://` 的 module import 會被擋掉).
- 沒有測試框架, 也沒有安裝任何套件的管道. 檢驗方式必須自帶.
- 語音合成是非同步且不可觀測的外部能力: 沒有辦法可靠地斷言「有沒有發出聲音」, 只能觀測我們自己維護的播放狀態.

動機見 proposal.md - Why.

## Goals / Non-Goals

**Goals:**

- 維持「一個檔案, 打開就能用」這個特性不變
- 狀態流向單純到不需要框架: 一份資料, 一個重繪函式
- 依序播放的中止行為必須確定 (deterministic), 不能因為 cancel 觸發的 end 事件而繼續往下唸
- 選取在清單變動後必須仍然對應到原本那幾個句子, 不能悄悄移到別句上
- 清單與選取資料損毀時不能讓整頁失效

**Non-Goals:**

- 不做 DOM 差異更新 (diffing) 或虛擬清單; 練習用的句子量級是數十句
- 不抽象出 storage / player 的介面層, 目前各只有一個實作
- 不做全選 / 反選, 也不做以選取為單位的批次刪除; 選取只決定播放範圍
- 不為語音合成本身寫自動化測試

## Decisions

### D1: 維持單一 HTML 檔, 不新增任何 dependency 與 build step

所有新增的 markup, 樣式與程式碼都寫在現有的頁面裡, 不拆檔, 不引入框架與套件.

- **Why**: 現在的使用方式是直接開檔; 拆成 ES module 會讓 `file://` 下的 import 失效, 等於強迫使用者跑一個 local server, 為了這個規模的功能不值得.
- **Trade-off**: 程式碼與 markup 集中在一份檔案, 檔案會變長; 以目前的功能量還在可讀範圍.

### D2: 輸入區改用 form 加單行 input, Enter 送出

把現有的 textarea 換成包在 form 裡的單行 input, 搭配一顆新增鈕.

- **Why**: 新增句子是高頻的重複動作, form 的原生行為直接提供 Enter 送出與 reset, 不必自己接鍵盤事件.
- **Trade-off**: 不再能一次貼上多行文字; 本次的操作模型本來就是一次加一句.
- **Alternative (rejected)**: 保留 textarea 並自己處理 Ctrl+Enter 送出 - 要多寫鍵盤處理, 而且 Enter 換行與 Enter 送出的預期會互相打架.

### D3: 狀態是一個字串陣列, 每次變動就整份重繪清單

所有清單操作 (新增, 刪除, 清空, 從本機載入) 都是對同一個陣列做變動, 變動後呼叫同一個 render 函式重畫整份清單, 並寫回本機儲存.

- **Why**: 只有一份資料來源, 畫面永遠是它的函式, 不會出現「陣列刪掉了但 DOM 還在」這種不同步的 bug.
- **Trade-off**: 每次變動都重建整份清單的 DOM; 這個規模下代價可以忽略.

### D4: 清單內的播放與刪除用事件委派

清單容器上掛一個 click handler, 用被點擊元素帶的索引 (index) 決定要播放或刪除哪一句, 而不是為每個項目各自綁事件.

- **Why**: 與 D3 的整份重繪天生相容 - 重繪會丟掉舊節點, 逐項綁事件等於每次重繪都要重綁.

### D5: 二次確認用瀏覽器原生的 confirm

單句刪除與清空全部都在動資料之前呼叫原生 confirm, 回傳 false 就直接結束, 不做任何變更.

- **Why**: 零 markup, 零樣式, 阻塞式回傳值讓刪除流程維持直線, 不需要 callback 或狀態機.
- **Trade-off**: 外觀由瀏覽器決定, 無法配合頁面樣式; 使用者若在瀏覽器勾選「不要再顯示對話框」, 確認會失效.
- **Alternative (rejected)**: 原生 `<dialog>` 元素 - 外觀可控, 但要多一份 markup, 開關邏輯與非同步的結果傳遞. 若之後在意外觀, 這是預設的升級路線.

### D6: 依序播放用 utterance 結束事件串接, 並以播放序號判斷是否續播

按下依序播放時記下一個遞增的播放序號, 每一句結束時只有序號未變才唸下一句. 中止 (再按一次, 按單句播放, 任何清單變動) 一律遞增序號並呼叫 cancel.

- **Why**: 呼叫 cancel 時, 瀏覽器仍會對被中斷的那句觸發結束事件. 如果結束事件無條件往下一句走, 中止就會失效, 反而聽到下一句. 用序號比對可以讓「這個結束事件屬於哪一輪播放」變成可判斷的事實, 而不是靠時間差猜.
- **Trade-off**: 播放狀態多了一個要維護的變數; 換來的是中止行為確定.
- **Alternative (rejected)**: 用單純的布林旗標 - 在「中止後立刻又開始新一輪」的情境下, 舊的結束事件會被誤認成新一輪的事件.

### D7: 清單存在本機儲存的單一 key, 解析失敗退回空清單

以 JSON 陣列存一個 key, 讀取時包在 try 裡, 解析失敗或型別不對就當成空清單.

- **Why**: 與現有語速/音色的保存方式一致. 讀取失敗的保護不是防禦性寫法, 而是必要的: 程式碼全部在同一段 script 裡, 一個未捕捉的解析錯誤會讓整頁的功能都不會啟動.
- **Trade-off**: 損毀的資料會被靜默丟棄而不是嘗試修復; 這裡的資料是可以重打的練習句子, 不值得為它寫修復邏輯.

### D8: 檢驗方式是頁面內的 assert 自我檢查, 瀏覽器與 node 兩條路都能跑

把清單的純邏輯 (新增時的去空白與空字串判斷, 依索引刪除, 選取切換與重映射, 播放佇列推導, 續播判斷, 從儲存字串還原) 寫成不碰 DOM 也不碰儲存的小函式, 連同一段以 assert 為主的自我檢查, 一起放進一個獨立且帶 id 的 script 區塊. 這個區塊有兩種執行方式:

- 瀏覽器: 網址帶特定查詢參數時執行, 結果輸出到 console
- node: 一段腳本依那個 id 把區塊的原始碼切出來後直接執行自我檢查, 跑的是頁面真正出貨的那份程式碼, 不是複製品

- **Why**: 專案裡沒有測試框架. 純函式加上網址參數開關是不需要新增任何工具就能重複執行的檢驗.
- **Why**: 純邏輯獨立成自己的 script 區塊, 正是「切出來執行」能成立的前提 - 區塊裡不能有任何 DOM 或儲存的參照, 否則在 node 裡會炸. 這個限制同時也讓純邏輯不會慢慢混進畫面的事情.
- **Trade-off**: node 那條路靠字串比對切出區塊, 區塊的 id 因此變成一個不能隨手改的約定.
- **Alternative (rejected)**: 把純函式拆成 ES module 檔案讓 node 直接 import - 這正是 D1 排除的做法, 會讓 `file://` 直接開啟失效. 切出來執行拿到同樣的好處而不用付這個代價.
- **Alternative (rejected)**: 引入測試框架與 jsdom - 為了幾個純函式而讓一個零依賴的單檔專案長出 package manager 與 node_modules, 代價遠大於收益.

### D9: 選取狀態是一組索引, 存在 JS 狀態裡, 刪除時做索引重映射

選取以一個索引集合表示, 句子本身維持單純的字串陣列. 勾選控制的勾選與否由 render 依這個集合決定, 而不是反過來從 DOM 讀. 刪除句子時用一個純函式把集合重新映射: 被刪的索引移除, 大於它的索引各減一.

- **Why**: 選取如果以 DOM 的勾選狀態為準, 會與 D3 的整份重繪直接衝突 - 重繪丟掉舊節點, 使用者只要新增一句就會清掉全部勾選. 狀態在 JS, 畫面是它的函式, 重繪就不會吃掉任何東西.
- **Why**: 索引集合讓句子維持字串陣列, 儲存格式, 新增與刪除的純函式都不用改, 而唯一的代價 (刪除時的重映射) 集中在一個地方, 而且是純函式, 可以直接被 assert 蓋住.
- **Trade-off**: 刪除路徑多一個必須記得呼叫的步驟; 漏掉的話勾選會移到別句上, 這正是 spec 裡「刪除句子後選取仍對應原本的句子」要擋的情境.
- **Alternative (rejected)**: 讓句子帶穩定 id, 選取存 id 集合 - 結構上更乾淨且永遠不用重映射, 但陣列要從字串改成物件, 儲存格式, 純函式與自我檢查全部跟著改, 還多一個產生 id 的來源. 以目前的規模, 一行重映射比較划算.
- **Alternative (rejected)**: 用句子文字當 key - spec 明確允許重複句子, 兩句一樣就會一起被選中, 是錯的.

### D10: 選取與句子一起保存, 用相鄰的第二個 key, 載入時過濾超出範圍的索引

選取以 JSON 陣列存進另一個 key, 與句子清單的 key 並列. 載入時除了 D7 的解析防護, 再多一道過濾: 丟掉超出目前清單長度的索引.

- **Why**: 兩個 key 讓句子清單的儲存格式維持 D7 的單純 JSON 陣列, 不必為了塞選取而改成物件.
- **Why**: 過濾不是多餘的防禦 - 索引的意義依附於清單長度, 兩個 key 一旦不同步 (手動改過, 或寫入中斷), 就會拿到指向不存在項目的索引.
- **Trade-off**: 兩個 key 理論上可能不同步; 兩者都在同一個寫回點以同步方式寫入, 加上載入時的過濾, 這個風險已經收斂.

### D11: 播放佇列在按下依序播放的當下就決定

按下依序播放時依當時的勾選算出佇列並固定下來, 之後這一輪播放都用這份佇列; 播放中變更勾選不影響進行中的序列, 下一次按下才生效.

- **Why**: 佇列固定下來之後, D6 的播放序號就有明確的對應對象, 「唸到第幾個」是一個單純的索引; 若佇列在播放中會變動, 位置的意義會跟著漂移.
- **Trade-off**: 播放中調整勾選不會即時反映; 這反而是比較好預測的行為, 使用者不會因為手滑勾到東西就改變正在進行的播放.

## Testing Seams

**主要 seam: 頁面內的清單純函式 (自我檢查, 見 D8 的兩種執行方式)**

清單與選取的狀態轉換是這次唯一有分支的邏輯, 也是最值得被檢驗的部分. 把它做成不碰 DOM, 不碰 storage 的純函式後, 一段 assert 就能涵蓋:

- 新增時去空白, 空字串不新增
- 依索引刪除只影響該項且順序不變
- 清空後為空
- 刪除後的選取索引重映射 (D9): 被刪的移除, 大於它的往前搬一格
- 播放佇列的推導 (D11): 有勾選時取勾選的那幾句, 沒有勾選時取全部, 且一律依清單順序
- 還原時的兩道防護: 損毀字串退回空的 (D7), 超出清單長度的選取索引被丟掉 (D10)

選在這一層是因為它是「還能被自動斷言」的最高層: 再往上就是 DOM 與語音合成, 兩者在這個沒有測試框架的專案裡都只能靠人眼與耳朵.

因為 D8 的區塊在 node 下也能執行, 這個 seam 是可以被腳本重複呼叫的, 不必每次都開瀏覽器.

**其餘行為: 逐項手動驗收**

確認 dialog 的取消路徑, 依序播放的串接與中止, 播放中刪除句子, 播放鈕標籤, 以及重新整理後的還原, 都靠 tasks.md 每個 slice 附的手動驗收步驟確認. 這些行為的驗證成本是「按幾下按鈕聽一下」, 為它們建立 mock 的成本遠高於此.

## Migration Plan

- **行為變更**: 原本「在 textarea 打字後直接按播放」不再存在, 使用者必須先把句子加入清單. 這是刻意的取捨, 見 proposal.md.
- **既有資料**: 語速與音色的本機儲存項目沿用原本的 key 與格式, 不變動, 不需要轉換.
- **新資料**: 清單與選取各使用一個新的 key. 舊使用者第一次開啟時兩個 key 都不存在, 依 D7 與 D10 分別視為空清單與沒有勾選, 因此沒有 migration 步驟, 也沒有向下相容問題.
- **rollout**: 單檔應用, 換檔即完成, 沒有先後順序需求.

## Risks / Trade-offs

- **確認 dialog 可被瀏覽器停用**: 使用者若在重複跳出時勾選「不再顯示對話框」, 之後的刪除會直接執行. 這是 D5 的已知上限, 觸發條件是短時間內連續大量確認, 一般使用不會遇到. 若成為實際問題, 升級路線是 D5 的 `<dialog>` 方案.
- **語音合成長時間播放會被瀏覽器中斷**: 部分瀏覽器在連續朗讀約十幾秒後會自行停住. 練習句子多為短句, 且依序播放是逐句送出而非一次送整段, 每句都重新開始, 因此風險低. 若真的遇到, 處理方式是在句子間加入極短的間隔.
- **音色清單載入時機**: 音色在部分瀏覽器要等事件才拿得到, 這是現有程式已處理的既有行為; 本次不改動這段, 但新增的播放路徑必須沿用同一個取得音色的方式, 不要自己另外抓一次.
- **殘留的勾選會改變播放範圍**: 勾選會活過重新整理 (D10), 使用者下次開啟時可能還留著上次的勾選, 按下依序播放卻只唸那幾句, 而原因在畫面上不明顯. 緩解方式是依序播放鈕直接把播放範圍寫在標籤上 (見 speech-playback 的「依序播放鈕標示播放範圍」), 讓這個狀態不是隱形的.
- **自我檢查沒有自動觸發**: 見 D8. 瀏覽器那條路要人主動開網址; node 那條路已經可以被腳本或 CI 呼叫, 但本專案沒有 CI, 所以實際上仍然靠人記得去跑. 對這個規模的專案是可接受的取捨.
- **切區塊的約定會被改壞**: node 那條路靠 script 區塊的 id 定位, 有人重新命名或把純函式搬出區塊, 檢查會安靜地失去覆蓋範圍而不是報錯. 這是 D8 用「不拆檔」換來的代價.

## Open Questions

- 確認 dialog 的外觀是否需要與頁面一致? 目前預設用原生 confirm (D5); 若在意外觀, 改用 `<dialog>` 的成本是多一段 markup 與開關邏輯.
- 清單是否需要在依序播放時標示目前唸到哪一句? 目前列為不做 (見 proposal.md). D6 的播放序號與 D11 的佇列合起來已經握有這個資訊 (佇列存的是清單索引), 之後要加只是多一個樣式切換.
- 勾選與播放範圍以外的用途 (例如以勾選為單位刪除) 目前刻意排除; 若之後要加, D9 的索引集合可以直接餵給刪除路徑, 但刪除多筆時的重映射會比單筆複雜, 屆時值得重新評估 D9 拒絕過的穩定 id 方案.
